## RFC: Preserve full tool results when truncated — auto-save to file + path in truncation marker

**Issue:** #1615

### Summary

When a tool result exceeds the per-call token cap, `truncateForModelByTokens` removes the middle and inserts a `[…truncated ~N tokens …]` marker. The full result is lost — never saved anywhere. The model can only re-issue the call with narrower scope and hope the truncated part comes back. For read-only tools (`read_file`, `web_search`) this is wasteful; for non-idempotent tools it's wrong.

This RFC proposes: when truncation occurs, write the full result to a predictable file and include the path in the truncation marker, so the model can `read_file` the complete result if needed.

---

### Design

#### Storage location

```
<project-root>/.reasonix/truncated-results/
├── 1745812345678-a1b2-web_search.txt
├── 1745812350123-b9f8-read_file.txt
└── …
```

- `<project-root>/.reasonix/` is already inside the sandbox → `safePath` passes without approval gate
- **Flat directory** (no session subdirectory — threading `sessionName` into `dispatch()` adds unnecessary plumbing for this use case)

#### Filename

```
<timestampMs>-<uuidPrefix8>-<toolName>.txt
```

- `timestampMs` — `Date.now()`, provides chronological sorting
- `uuidPrefix8` — `crypto.randomUUID().slice(0, 8)`, 8 hex chars eliminates collision risk even within the same millisecond
- `toolName` — `sanitizeName()` processed tool name

Examples:
```
1745812345678-a1b2c3d4-web_search.txt
1745812345678-a1b2c3d5-read_file.txt
1745812350123-b9f8e7d6-read_file.txt
```

No shared counter, no persistence, no resume-recovery needed.

#### Truncation marker change

Current:
```
[…truncated ~1,247 tokens (42,971 chars) — raise BridgeOptions.maxResultTokens, or call the tool with a narrower scope (filter, head, pagination)…]
```

Proposed:
```
[…truncated ~1,247 tokens (42,971 chars) — Full result saved at: .reasonix/truncated-results/1745812345678-a1b2-web_search.txt — read_file to recover complete data…]
```

#### Save trigger

Only one dispatch-time truncation site needs the save logic:

**`ToolRegistry.dispatch()`** — `src/tools.ts:308-313`
- Full result exists in variable `str` before truncation
- Has access to tool `name` and `opts`
- Two caps applied in series: token then char. If `clipped !== str` after both, dispatch saves the **original** `str` once.

**Design decision — dispatch-level save, not callback in truncation functions:**
Both `truncateForModelByTokens` and `truncateForModel` gain an optional **third `extraNote?: string`** parameter instead of a callback. When truncation actually occurs, `extraNote` is appended after the truncation marker text. This approach:
- Keeps the save orchestration in dispatch (single point, avoids double-save on dual truncation)
- Avoids coupling truncation functions to filesystem or tool metadata
- Lets dispatch inject the saved file path into the marker

```typescript
// Before: 2-arg
export function truncateForModelByTokens(s: string, maxTokens: number): string
// After: 3-arg, backward compatible
export function truncateForModelByTokens(s: string, maxTokens: number, extraNote?: string): string
```

- If truncation actually occurs → `extraNote` is appended to marker line
- If no truncation → string returned unchanged, `extraNote` never used
- The saved content is the **untruncated original** (saved before truncation in dispatch)

**Non-target — MCP tools (`flattenMcpResult`):**
Deferred. The `flattenMcpResult` path lacks `rootDir` information without threading it through `BridgeEnv`. Scoping to built-in tools covers the primary use case (`web_search`/`web_fetch`/`read_file`).

**Non-target — healing paths** (`src/loop/shrink.ts:29,54`):
These operate on already-persisted (already-truncated) messages — no original to save. No change needed.

#### Security

New optional field on `ToolDefinition`:
```typescript
skipTruncationSave?: boolean;
```

Candidates for `skipTruncationSave: true`:
- `get_env` / `everything_get-env` — may leak API keys
- All write tools (`write_file`, `edit_file`, `multi_edit`, etc.) — typically return short confirmations; saving large truncated write results has marginal value

Saved files get `chmod(0o600)`, matching the session file permission model.

#### Cleanup

TTL-based: remove files older than 30 days (runs as a cheap stat + rm at startup or on first save).

Neither urgent — with average file size ~50KB, even 1000 files consume only ~50MB.

### Change Assessment

#### Public API compatibility

| Export | File:Line | Nature | Breakage |
|---|---|---|---|
| `truncateForModel` | `src/index.ts:228` | Public API | ⚠️ Adding optional 3rd param — backward compatible |
| `truncateForModelByTokens` | `src/index.ts:229` | Public API | ⚠️ Same — backward compatible |
| `ToolDefinition` interface | `src/tools.ts` | Public API (type) | ⚠️ Adding optional field — backward compatible |

Existing 2-arg callers keep working unchanged.

#### Call sites risk matrix

| File:Line | Needs save? | Risk |
|---|---|---|
| `src/tools.ts:310` (dispatch token clip) | ✅ Yes (via extraNote) | **Medium** — hot path, conditional (only large results) |
| `src/tools.ts:313` (dispatch char clip) | ✅ Yes (via extraNote) | **Medium** — same |
| `src/mcp/registry.ts:218` (flattenMcpResult) | ❌ Deferred | **None** |
| `src/loop/shrink.ts:29,54` (healing) | ❌ No | **None** |

#### Performance

| Operation | Cost |
|---|---|
| `mkdirSync` (once) | ~0.1ms |
| `writeFileSync` (avg 50KB) | ~1ms (SSD) |
| `chmodSync` | ~0.05ms |
| **Per truncated call** | **~1-2ms** |

Truncation is rare (most results fit in 8K tokens) — cost negligible vs 5-30s API round-trips.

#### Security risk

| Risk | Severity | Mitigation |
|---|---|---|
| Tool result contains API key → saved to disk | Medium | `skipTruncationSave` on `get_env`; 0o600 |
| Project `.reasonix/` gets committed | Low | Add to `.gitignore` |
| Shared workstation read access | Low | 0o600; same model as session JSONL |

Note: session JSONL already persists truncated tool results — this incrementally exposes the full version, not from zero.

#### Test impact

- `tests/truncate-tokens.test.ts` — no change (no 3rd arg passed); regex `truncated ~?(\d+) tokens` still matches
- `tests/bundle-smoke.test.ts` — no change
- `tests/public-api.test.ts` — no change
- **New**: `tests/truncated-result-saver.test.ts` — save path format, skip flag, edge cases (~40 lines)

#### Rollback

1. Revert function signatures to 2-arg
2. Delete `src/tools/truncated-result-saver.ts`
3. Remove cleanup logic
4. **Zero migration** — leftover files on disk are harmless, can be `rm -rf`'d anytime

### Braindates / Decisions Log

| Question | Decision |
|---|---|
| **Callback or extraNote?** | `extraNote?: string` third param — dispatch orchestrates save, truncation functions only append text |
| **Double-save on dual truncation?** | dispatch saves original `str` ONCE after both truncations run |
| **Session subdirectory?** | Flat — no session name needed at dispatch level |
| **MCP tools?** | Deferred — scope to built-in tools only |
| **`skipTruncationSave`?** | Yes — `ToolDefinition` optional field |
| **TTL?** | 30 days, run at startup or first save |
