# Session titles: ownership and resolution

A session has two identities that must not be conflated:

| | what it is | where it lives | user-visible |
|---|---|---|---|
| **store identity** | immutable durable key: the v4 session id (32-hex random, or a 24-hex digest for migrated sessions) | the store directory name, `manifest.json` | never |
| **display name** | what a listing renders for a human | resolved from the session's own durable facts | always |

The v4 cutover separated them; before it, a session's identity *was* its filename, so a
listing could use one value for both. Any surface that still renders the store id is a
surface that has not been taught the difference. It is the same reader/writer split behind
the CLI resume reports (#10422, #10488, #10405, #10421) and behind #10533 for `serve`.

## Resolution ladder

One ladder, ordered by how much the fact can be trusted:

1. **Explicit title** - a `session/title` event in the v4 event log, written by a user
   rename or by the agent's `set_session_title` tool. Durable, authoritative, outranks
   anything generated. Carries a revision (`TitleSequence`) so a concurrent generated
   title cannot overwrite it.
2. **Generated title** - a short LLM summary of the first user message. Derived, and
   disposable *only if it can be regenerated*; see ownership below.
3. **First authored message** - `SessionInfo.Preview`, always derivable from the durable
   log, never persisted separately. Host-injected blocks are already stripped.
4. **Store id** - the identity, the last resort, and correct only when nothing at all is
   known yet. A listing should reach this during the catalog rebuild window and nowhere
   else.

Rungs 1-3 have no stability guarantee to offer a user *during* the rebuild window; the
honest options are the id or an explicit "indexing" placeholder. Consumers must not invent
their own silently-divergent placeholder for that window (the CLI does, `resume_native.go`).

## Ownership (the defect)

A generated title currently has **two owners with different durability**:

- the store writes `session/title` events, durably (`Service.SetTitle`,
  `Service.SetTitleIfSequence`, cold targets supported - a cold write takes the writer
  lease, commits, and releases);
- `serve` generates its own titles with a separate flash provider and writes them to
  `<store root>/.session-titles.json`, a machine-local file outside the event log.

The cache is therefore not a cache of the durable title; it is a **parallel title store**.
Consequences, all observed:

- a title generated by `serve` does not survive migration and is invisible to every other
  reader (the CLI resume picker reads `SessionInfo.Title` and the preview, never this file);
- the file is keyed by legacy transcript file name or store id, so a migrated session's
  legacy entry cannot be matched even where the file survives;
- the cache has to be re-anchored by hand whenever the store layout moves, which is how
  #10533 arose: it was rooted at the legacy transcript catalog while v4 sessions and their
  titles live in the sibling `sessions-v4` store, so every v4 read saw an empty cache.

## Target shape

- **One durable owner.** `session/title` is the only place a title is stored. Generation is
  an enrichment that *writes through* with `SetTitleIfSequence` and the revision it read,
  so a rename racing a generation wins.
- **One read contract.** Title resolution belongs to the session read model
  (`SessionInfo`), not to each transport's list handler. A client that needs a name asks
  the store, and every transport renders the same ladder.
- **The JSON file stays a cache.** Its only job is to avoid re-spending a generation
  request while the first message is unchanged. Deleting it must cost requests, never
  information.
- **Generation is not a GET side effect.** Writing durable state from a list poll is a
  wart; the eventual shape generates on turn completion (or an explicit rename), so a
  listing is a pure read. Until then, a write-through on first sight is bounded: after it
  succeeds the durable title exists, so it does not repeat.

## Migration

The v4 migration bridge imports legacy sessions and deletes the sources, but carries no
title: `BranchMeta.CustomTitle` and `TopicTitle` both reach the v4 store empty while the
sidecar holding them is deleted (verified on the JSONL path; the sessions-v3 path has no
title handling either). Migration is where data actually dies, so it - not the display
path - owns this fix. `migration-map.json` records `sourcePath` to `targetId`, which is
enough to re-key both a legacy title and a legacy generated-title cache.

Note for any fix: `internal/session/import_resolver.go` groups `session/title` with
`session/config` and `diagnostic` as *not meaningful* when deciding whether an import
carries content. A migrated title would be discarded as noise on any import path that
consults that classification, so it must be revisited alongside the fix.
