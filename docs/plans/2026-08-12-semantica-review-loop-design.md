# Semantica 第二阶段设计：人工复核闭环

## 目标与约束

把第一阶段的一次性语义资产体检结果变成可持续处理的企业治理事项。管理员可以将候选标记为“确认需治理”或“保留为独立记录”，决定在刷新、重启和再次检查后仍然可追溯。

本阶段不自动合并资产、不删除记录、不改写 Wiki、不确认图关系。“确认需治理”只表示候选真实且需要后续人工治理，不表示已经完成资产合并。

## 方案选择

采用 SQLite 独立复核表，并由同一事务保存决定与审计事件。候选使用“类型 + 排序后的资产标识 + 冲突字段”的确定性指纹；相同候选再次出现时只更新最近发现时间，既有决定不会被重新打开。

未采用以下方案：

- 只写审计事件并从日志反推当前状态：查询复杂，无法可靠表达当前待办；
- 把状态写回正式资产：会把算法候选与正式知识事实混在一起；
- 新增外部任务服务：小微版运维成本超过收益。

## 状态与数据

复核记录只有三个状态：

1. `pending`：等待管理员判断；
2. `confirmed`：已确认需要治理，等待后续人工合并或纠正；
3. `dismissed`：确认两项记录应独立保留，或该冲突无需处理。

只允许 `pending` 一次性转为 `confirmed` 或 `dismissed`。已决定记录不能通过普通接口改判；新的候选指纹会创建新的待复核记录。

记录只保存经过白名单裁剪的候选摘要：资产标识、标题、冲突字段、有限值、相似度、有限原因、引擎版本和时间。不保存原始文档、证据引文、密码、会话或 API 密钥。管理员备注限制为 300 字。

## 接口与权限

- `GET /api/admin/semantic/reviews`：管理员读取当前工作空间复核记录；
- `POST /api/admin/semantic/reviews/:id/decision`：管理员提交一次性决定；
- `POST /api/admin/semantic/enrich`：检查后由服务端直接写入候选，浏览器不能自行提交候选内容；
- `/api/admin/operations`：返回最近复核记录，系统页刷新后可继续处理。

所有接口都先验证会话、管理员角色和当前工作空间。决定与 `semantic.review_confirm` / `semantic.review_dismiss` 审计事件在同一数据库事务中提交。

## 用户体验

系统状态页在每条候选下显示当前状态。待复核项提供“确认需治理”和“保留独立记录”两个动作；点击后进入确认对话框，可填写处理说明，并清楚说明不会自动合并或修改 Wiki。已决定项显示决定人、时间和备注，不再显示可变更按钮。

待办中心为管理员增加“复核语义资产建议”，指向系统状态页。非管理员看不到该待办和复核接口。

## 失败处理与非功能要求

- Semantica 不可用时仍可读取和处理历史复核记录；
- 单次最多落库 100 个候选，字段和 JSON 体积均有限制；
- 确定性指纹与工作空间唯一约束保证幂等；
- 复核决定、审计事件采用单事务，避免一边成功一边失败；
- 相同已决定候选再次出现时保留决定，仅更新 `lastSeenAt`；
- 列表最多返回 200 条，优先显示待复核项。

## 验收标准

- 存储测试覆盖幂等、终态、工作空间隔离、字段裁剪和审计原子性；
- 接口测试覆盖管理员成功、只读成员拒绝、无效输入和重复决定冲突；
- UI 契约测试覆盖状态、动作、确认对话框和业务化文案；
- 真实浏览器完成“检查 → 确认需治理 → 刷新后仍保留”的端到端流程；
- 全量测试、构建、依赖审计、凭据扫描和差异检查通过。
