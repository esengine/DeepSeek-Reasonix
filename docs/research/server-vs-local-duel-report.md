# 服务端 web_search vs 本地 web_fetch 对决报告

日期：2026-08-03 晚（北京时间）
工具：`cmd/dbg-usage/duel_smoke.go`（同主题双路径量化）
主题："2026年8月 全球AI算力芯片市场格局与竞争态势分析"

## 量化对比结果

| 维度 | retrieve_info（服务端 web_search） | web_fetch（本地抓取） |
|---|---|---|
| **深度-字数** | 4486B（缓存）/ 4511B（真实联网 1m41s） | 224B（example.com，本地网络受限） |
| **深度-事实数** | 19（联网）/ 29（AI 缓存） | 0 |
| **广度-来源** | 多来源蒸馏（隐含多页） | 单 URL 单页 |
| **可读性** | 结构化 markdown（标题/列表/关键事实段），评分 1.0-1.4 | 原始正文提取，评分 0.7 |
| **性能** | 缓存 10ms / 联网 1m41s | 本地 HTTP 677ms（仅 example.com 通） |
| **成本** | 服务端计算（搜索+蒸馏）≈0 本地资源；API 按 token 计费 | 本地下载原文 + 本地解析；无 API 计费，耗本地带宽 |

## 关键发现（驱动端差异实证）

### 1. 本地网络受限 → web_fetch 大面积不可用

```
实测：wiki（IPv6 重置）→ IPv4 fallback 修复后仍超时
      reuters/bbc（连接重置/超时）
      仅 example.com 可达（224B）
```

**服务端 web_search 不受此限制**（DeepSeek 服务器爬取）——受限网络下
retrieve_info 依然可用，web_fetch 基本失效。这是驱动端差异的直接实证：
服务端检索把网络依赖转移到服务端。

### 2. 修复：web_fetch 只拨 ips[0]（IPv6 优先失败即弃）

```
directDialContext 用 ips[0] → IPv6 被重置时不试 IPv4 → 全失败
修复（1a62c2f31）：遍历所有解析 IP 逐个尝试，SSRF 检查保持
实测：wiki 从 connection reset 变为 IPv4 拨号（虽仍超时，机制已修）
```

### 3. 服务端蒸馏不含 http 链接

```
retrieve_info 输出无 URL（来源是文字描述）——web_fetch 无法自动
从服务端结果取 URL，需预设权威 URL（本测试 fallback example.com）
```

## 结论

| 场景 | 胜者 | 原因 |
|---|---|---|
| 受限网络信息查询 | **服务端 web_search** | 网络依赖在服务端，本地零流量 |
| 原文细节获取 | **web_fetch**（网络可达时） | 服务端摘要有损，本地拿原文 |
| 成本敏感（本地带宽） | 服务端 | 客户端零下载 |
| 成本敏感（API token） | 本地（网络可达时） | 无 API 计费 |

**分工确认**：服务端负责检索+蒸馏（可用性/结构化优先），本地负责原文补充
（细节优先）——不是冗余，是驱动端能力互补。
