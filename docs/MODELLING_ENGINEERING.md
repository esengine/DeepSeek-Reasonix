# Modeling Engineering — 建模工程优化设计

> 定位：对 **agent 建模过程**（工作流/工具调用/上下文组装/状态管理）做工程化、精准化优化——
> 缓存命中、token 消耗、可审计与故障恢复（事件溯源）、轨迹数据复用。先文档后实施。
> 约束：正确性优先（交付模式 gate），有项目风险的方案不默认引入。

## 1. 四大优化面

| # | 面 | 目标 | 现状 | 缺口 |
|---|---|---|---|---|
| 1 | 缓存命中 | 幂等重复调用短路 + 前缀稳定 | toolcache（工具结果）+ 前缀稳定（system 静态/schema 排序/命中统计/预热器） | 语义缓存（仅限重复建模场景，见 §2） |
| 2 | token 消耗 | 规划/上下文 token 最小化 | compaction（10-section 隐式状态）、工具缓存、前缀稳定 | 轻量模式接入（见 §3） |
| 3 | 可审计与故障恢复 | 精确重放 + 崩溃点恢复（运行 20h 中断可继续） | flywheel Sink 事件流（genai.event.v1）+ session events.jsonl | 重放/恢复执行器（见 §4） |
| 4 | 轨迹数据（Co-training 基础） | 工具调用/多智能体轨迹沉淀为定制优化素材 | flywheel Trajectory/Store + BM25 检索 + Judge 标签 | 导出/蒸馏接口（见 §5） |

## 2. 语义缓存：适用场景与正确性边界

**它解决什么**：用户提问/建模请求的**语义相似性**——`"对 X 做缓存优化"` 与 `"优化 X 的缓存"` 结构不同但意图相同。精确 key 无法命中；语义聚类把相似请求路由到**同一预置执行计划（plan）**，跳过 LLM 规划阶段，直接执行历史链路。

**什么时候有用（你的判断成立）**：
- **重复建模场景**：用户反复对相似目标建模（如"给模块 A/B/C 都做缓存命中优化"、"对多个函数做 token 优化"）——语义相似 → 命中历史 plan → 省掉每次的规划 token（规划通常占单次请求 token 的 10-30%）。
- **轻量模式**：轻量模式本身以省 token 为目标；语义缓存命中 = 跳过规划 = 双倍省 token，是轻量模式的天然搭档（`P2.1` 细化的结论：**语义缓存应当挂在轻量模式的建模领域**，面对重复建模时启用）。

**为什么按原则不默认引入**：
- 依赖：embedding 需要向量化（本地零依赖偏好冲突；本机无 embedding 服务）。
- 正确性：语义误判会把"看似相似实则不同"的请求路由到错误 plan（**比缓存过期更危险**——直接执行错误计划）。

**若要引入（用户明确要求时的安全形态）**：
1. 相似度阈值保守（如 ≥0.92）+ 命中后**展示 plan 摘要供确认**，确认后才执行（不自动执行）。
2. 只对**建模类**请求启用（明确领域标记），不泛化到任意查询。
3. fallback：无命中/低置信 → 常规规划（语义缓存只是加速器，不是决策器）。
4. 度量：只统计"省了多少规划 token"，不刷命中率。

## 3. 轻量模式接入（token 消耗优化）

- 轻量模式（省 token 模式）下：
  - 复用 §2 语义缓存命中（若有）+ 现有 toolcache；
  - 规划阶段压缩：预置 plan 模板 + 只补差异（delta prompt）；
  - 上下文裁剪：只注入与当前步骤相关的历史（BM25 检索 flywheel 轨迹/记忆，替代全量历史）。
- 度量目标：轻量模式下单次建模请求 token 消耗 ≤ 常规模式 50%。

## 4. 可审计与故障恢复（Event Sourcing，借鉴 Muse Code）

**架构（已有基础，强化为闭环）**：
- 每次**模型调用 / 工具运行 / 审批 / 编辑**追加本地事件日志（现有：flywheel Sink `genai.event.v1` + session `events.jsonl` + ToolResult 含 DurationMs/Err）。
- **精确重放**：从事件流重建任意时刻状态（`replay` 执行器：读事件 → 重放工具调用/消息 → 恢复会话）。
- **崩溃恢复**：记录 checkpoint（每 N 步/每关键状态快照）→ 重启时从最近 checkpoint 恢复，不从头开始（对应"运行 20 小时后中断仍可继续"）。
- 现状缺口：①checkpoint 机制（agent 状态快照点）②replay 执行器 ③审批事件记录（Permission 决策事件）。

**交付（文档批准后）**：
- `internal/eventlog`：事件追加（已有 flywheel 复用）+ checkpoint 快照 + replay 重建。
- agent 接线：关键步骤（tool 批次完成/compaction/会话边界）写 checkpoint；启动时检测崩溃残留 → 恢复。
- 测试：20 步任务中途 kill → 重启 → 状态一致（精确重放断言）。

## 5. 轨迹数据（Co-training 基础，借鉴 Muse Spark 1.2）

- flywheel Trajectory（task→verify→judge）已沉淀工具调用/验证轨迹 + Judge 质量标签。
- **用途**：
  - 短期：成功轨迹 → few-shot 示例注入（CoSPlay 式蒸馏，P0 已列）；失败轨迹 → 记忆库。
  - 中期：`export` 工具导出标准化轨迹集（JSONL schema 固定）→ 供微调/RL 数据（对应 Muse Code 的"工具调用和多智能体协作轨迹融入训练"）。
- 交付：`flywheel.Export(dir, filter)`（按 judge 标签/任务域导出）+ schema 版本化。

## 6. 实施路线（文档先行）

1. **阶段 A（低风险，可直接做）**：事件溯源闭环——checkpoint + replay（§4）+ 审批事件记录；全仓测试守护。
2. **阶段 B（低风险）**：轨迹导出接口 + 轻量模式上下文裁剪（§5 + §3）。
3. **阶段 C（需用户确认）**：语义缓存（§2 安全形态）——有 embedding 依赖 + 路由正确性风险，按交付 gate 默认不做，仅在用户明确要求时实施。

## 7. 验证

- 每阶段：新增测试 + 全仓回归（基线 109 ok）。
- 事件溯源：崩溃恢复测试（kill 后状态一致）。
- 语义缓存（若做）：相似度阈值测试 + 误判 fallback 测试 + 规划 token 节省度量。
