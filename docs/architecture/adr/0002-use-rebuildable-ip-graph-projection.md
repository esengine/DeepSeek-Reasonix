# ADR-0002：使用可重建关系投影支持 IP 全景图与图搜索

## 状态

Accepted

## 日期

2026-08-10

## 背景

intelifar 已将发布资产、Wiki 版本和模型生成关系保存在 JSON 记录中，并通过内存字符串包含方式搜索。资产规模增长后，需要支持关系发现、影响分析、一至两跳搜索和全景网络展示，同时保持小微企业版本的部署简单性、审计完整性和权限隔离。

直接将图数据库作为主存储会增加部署、备份、事务一致性和运维成本；继续把关系保存在 Wiki JSON 中又无法提供稳定资产标识、关系生命周期和高效遍历。

## 决策

保留不可变发布快照、Wiki 版本和哈希审计链作为系统记录；在同一 SQLite 数据库中增加规范化的资产节点、关系边、关系依据、别名和全文查询投影。

图查询投影遵循以下原则：

- 可从正式发布记录幂等重建；
- 人工确认、拒绝和替代状态作为正式业务记录事务化保存；
- 全文搜索负责召回，图关系负责一至两跳扩展和可解释重排；
- 所有遍历在服务端先执行工作空间和资产可见性过滤；
- 小微企业版本限制遍历深度与返回节点数；
- 独立图数据库只在实际规模、算法或高可用需求证明 SQLite 不足后引入，并继续作为查询投影。

## 后果

### 正面

- 不增加小微企业首期基础设施，仍可获得真实图搜索和全景展示；
- 发布、版本、审计与关系查询职责清晰；
- 投影损坏可以重建，不会破坏正式资产；
- 搜索结果能够返回关系路径和原文依据；
- 后续可平滑投影到企业已有图数据库。

### 负面

- 需要维护投影一致性、重建工具和关系实体归一化；
- SQLite 递归查询必须限制深度和结果规模；
- 中文全文召回与图排序需要金标查询持续校准；
- 人工关系状态与可重建节点投影的边界需要严格测试。

### 中性

- 前端关系图不是数据源，只消费授权后的后端子图；
- AI 关系默认处于建议状态，不能直接进入正式搜索；
- 图数据库并未被否定，只是延后到存在可测量需求时采用。

## 备选方案

### 继续使用 Wiki JSON 关系

未采用。实现简单，但无法稳定解决别名、生命周期、依据、遍历、索引与权限过滤。

### 直接采用独立图数据库

暂未采用。图查询能力最强，但超出小微企业首期的一至两跳查询需求，会增加独立服务、备份、监控和一致性成本。

### 图数据库作为唯一主存储

拒绝。资产发布、版本和审计需要明确事务与不可变记录；将所有业务真相改为图模型会放大迁移和恢复风险。
