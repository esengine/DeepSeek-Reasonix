# ADR-0004：在正式资产之外持久化语义复核决定

## 状态

Accepted

## 日期

2026-08-12

## 背景

第一阶段 Semantica 体检只返回一次性候选。企业管理员需要在刷新或重启后继续处理，并证明谁在何时判断了候选。候选仍然只是辅助建议，不能直接改变正式资产、Wiki 或关系。

## 决策

在现有 SQLite 工作空间数据库中增加独立的 `semantic_reviews` 表：

- 以工作空间和确定性候选指纹保证重复检查幂等；
- 状态只允许 `pending` 转为 `confirmed` 或 `dismissed`；
- 决定与哈希审计事件在同一事务内提交；
- 再次发现相同候选只更新最近发现时间，不重新打开已决定事项；
- 只保存白名单候选摘要和有限管理员备注；
- `confirmed` 表示“确认需治理”，不表示“已合并”；
- Semantica 仍不是正式数据源，SQLite 正式资产和 Wiki 记录保持不变。

## 后果

### 正面

- 管理员获得可恢复、可筛选、可审计的复核闭环；
- 候选状态与正式知识状态保持清晰分离；
- 不增加新的常驻服务或部署单元；
- 检查失败不影响历史复核记录的读取和处理。

### 负面

- 需要维护新的数据表、状态迁移和管理界面；
- 已决定记录不能直接改判，纠错需要未来显式的重新打开流程；
- “确认需治理”之后的实际资产合并仍需后续功能。

### 中性

- 审计链继续作为不可变操作证据，但不承担业务状态查询；
- 生产版迁移到 PostgreSQL 时保留相同状态机和唯一约束。

## 备选方案

### 从审计事件重建复核状态

拒绝。审计日志适合证明发生过什么，不适合作为可变业务事项的查询模型。

### 把候选状态写入资产或 Wiki

拒绝。算法建议会污染正式知识记录，并扩大误操作影响。

### 引入独立工作流服务

暂不采用。小微版规模下会增加鉴权、部署、备份和监控责任。
