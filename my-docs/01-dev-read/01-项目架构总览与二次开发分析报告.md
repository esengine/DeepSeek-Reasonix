## 二、CLI 模式深度分析

### 2.1 命令树

```
reasonix
  ├── (无参数)        → welcome() + 首次运行引导
  ├── chat / code     → 交互式 TUI 会话（bubbletea）
  ├── run "prompt"    → 一次性执行（TextSink 输出到 stdout）
  ├── serve           → HTTP/SSE 服务
  ├── acp             → ACP stdio 服务（二开可砍掉）
  ├── setup / config  → 配置向导
  ├── mcp             → MCP 管理命令
  ├── doctor          → 诊断
  └── init            → /init 提示
```

### 2.2 TUI 架构（chat_tui.go）

- 基于 **bubbletea v2**，不使用 alt-screen，输出直接追加回滚缓冲区
- input + status + approval banner 是仅有的 bubbletea 管理区域
- Autocomplete：`/` 命令补全 + `@` 文件引用补全
- 事件驱动：agent 事件流经 `internal/event.Sink` → channel → `tea.Msg`
- `internal/cli/` 包已拆分为多个文件：bot.go、theme.go、md.go、complete.go、select.go、skill_picker.go、mcp_manager.go 等，不再全部集中在 chat_tui.go

**风险**：
1. **chat_tui.go 单文件 ~3,900 行（~130KB）** — 函数间耦合深，虽然已拆出部分逻辑到其他文件，核心渲染和状态管理仍在此文件
2. bubbletea v2 较新 — 中文社区资料少，调试需读源码
3. 事件类型 ~18 种，自定义渲染需理解每种含义
4. `/loop` 命令实现在 `loop.go`（88 行），仍为 `chatTUI` 的方法

### 2.3 `run` 模式的会话持久化

`reasonix run "prompt"` 已有基础的会话持久化（通过 `ctrl.Snapshot()` 在运行结束时保存），但缺少 TUI 模式的自动中间保存和恢复能力。`ctrl.Resume` 和 `ctrl.SessionPath` 基础设施完整。

## 三、Go 集成模式深度分析（核心）

> **Go 集成 = 将 Reasonix 作为 Go Module 导入**，直接调用 `boot.Build()` 取得 `*control.Controller`，通过其公共方法驱动 agent。ACP 是独立于 Go 集成之外的 stdio 前端，与 Go 集成路径无关。

### 3.2 boot.Build 组装流程

```
boot.Build(ctx, Options{...})
  ┌─ 配置层 ─────────────────────────────────┐
  │ 1. config.LoadForRoot(root) → TOML 配置   │  ← 依赖配置文件和环境变量
  │ 2. ResolveModel(modelName) → provider     │  ← 必须配置至少一个 provider
  ├─ 基础设施层 ──────────────────────────────┤
  │ 3. jobs.NewManager(sink)                  │
  │ 4. NewProviderWithProxy → LLM provider     │  ← 联网
  │ 5. 组合 system prompt (memory + skill)    │
  ├─ 工具层 ──────────────────────────────────┤
  │ 6. tool.NewRegistry → 注册中心             │  ← 核心：所有工具注册于此
  │ 7. 启动 MCP plugin Host (按 tier)         │  ← 可选
  │ 8. permission gate + policy               │  ← 支持多级审批策略
  ├─ 扩展层 ──────────────────────────────────┤
  │ 9. command.Load → slash 命令             │
  │ 10. hook.NewRunner → 生命周期钩子          │
  │ 11. memory.Set → 持久化记忆存储            │
  ├─ Agent 层 ────────────────────────────────┤
  │ 12. 构建 executor Agent                    │  ← 核心执行循环
  │ 13. 可选：planner_model → Coordinator      │
  │ 14. 可选：auto_plan_classifier             │
  └─ control.New → 返回 controller ───────────┘
```

`boot.Options` 结构体（`internal/boot/boot.go:58`）：

```go
type Options struct {
    Model          string          // 模型名称
    MaxSteps       int             // 最大执行步数
    RequireKey     bool            // 启动时要求设置 API key
    Sink           event.Sink      // 事件接收器

```

### 3.3 event.Sink 接口——你需要实现的核心接口

事件包独立于 `internal/event/`（非 agent 子包），提供解码所需的全部类型。

```go
// 你只需实现这一个接口来接收 agent 的完整输出
type Sink interface {
    Emit(event Event)
}
```

**Event 结构体（完整字段）：**

| 字段 | 类型 | 适用 EventKind | 说明 |
|------|------|----------------|------|
| `Kind` | `Kind` | 全部 | 事件类型标识 |
| `Text` | `string` | Reasoning / Text / Message / Notice / Phase | 流式文本内容 |
| `Reasoning` | `string` | Message | 完整思考链（最终消息） |
| `Tool` | `Tool` | ToolDispatch / ToolResult / ToolProgress | 工具调用/结果/进度 |
| `Usage` | `*provider.Usage` | Usage | 本轮 token 用量 |
| `Pricing` | `*provider.Pricing` | Usage | 定价信息（nil=不显示）|
| `CacheDiagnostics` | `*CacheDiagnostics` | Usage | 缓存命中/未命中诊断 |
| `SessionHit` | `int` | Usage | 会话累计缓存命中 |
| `SessionMiss` | `int` | Usage | 会话累计缓存未命中 |
| `Level` | `Level` | Notice | 通知级别（Info/Warn）|
| `Approval` | `Approval` | ApprovalRequest | 审批请求（ID/Tool/Subject）|
| `Ask` | `Ask` | AskRequest | 多选问题（ID + Questions）|
| `Err` | `error` | TurnDone | 错误信息（nil=正常结束）|
| `Compaction` | `Compaction` | CompactionStarted/Done | 上下文压缩信息 |
| `RetryAttempt` | `int` | Retrying | 当前重试次数（1-based）|
| `RetryMax` | `int` | Retrying | 最大重试次数 |

**EventKind 完整列表（18 种）：**

| Kind | 触发时机 | 关键负载 |
|------|---------|---------|
| `TurnStarted` | 每轮开始 | 无（sink 重置状态）|
| `Reasoning` | 模型思考中 | Text（流式推理片段）|
| `Text` | 模型回答中 | Text（流式文本片段）|
| `Message` | 回答完成 | Text（全文）+ Reasoning（完整推理链）|
| `ToolDispatch` | 工具调用开始 | Tool（ID/Name/Args/ReadOnly/Partial/FileDiff/Profile）|
| `ToolResult` | 工具调用完成 | Tool（+ Output/Err/Truncated/DurationMs）|
| `ToolProgress` | 长工具中间输出 | Tool（ID + Output 新块）|
| `Usage` | 每轮 token 统计 | Usage + Pricing + CacheDiagnostics + SessionHit/Miss |
| `Notice` | 警告/通知 | Level + Text |
| `Phase` | 协调器阶段边界 | Text（标签，如 "deepseek · planning"）|
| `ApprovalRequest` | 等待审批 | Approval（ID/Tool/Subject）|
| `AskRequest` | 等待用户选择 | Ask（ID + Questions）|
| `TurnDone` | 本轮结束 | Err（nil=正常，非nil=失败，Cancel 也返回 nil）|
| `CompactionStarted` | 开始压缩 | Compaction（Trigger）|
| `CompactionDone` | 压缩完成 | Compaction（+Messages/Summary/Archive）|
| `MCPSurfaceReady` | MCP 资源就绪 | Text（"<server>: <surface> ready"）|
| `Retrying` | provider 重试 | RetryAttempt / RetryMax |
| `Steer` | 中间指引投递 | Text（指引内容）|

事件流生命周期（单轮）：
```
Send("写一个测试") →
  TurnStarted → Reasoning* → Text* → ToolDispatch → ToolProgress* → ToolResult
  → Reasoning* → Text* → ToolDispatch → ApprovalRequest ← 需审批
  → ToolResult → ... → TurnDone{Err: nil}
```

**重要**：
- `ApprovalRequest` 事件需要你通过 `ctrl.Approve(id, true, ...)` 回复，否则 agent 会阻塞等待。
- `AskRequest` 事件需要你通过 `ctrl.AnswerQuestion(id, answers)` 回复。
- 工具调用支持 `Partial=true` 的提前下发 + 完整 `Partial=false` 的下发两阶段，使前端可以立刻显示卡片。

### 3.4 Go 集成的典型用法

```go
// 1. 准备 event sink
type mySink struct{ ch chan event.Event }
func (s *mySink) Emit(e event.Event) { s.ch <- e }

// 2. 组装 controller
sink := &mySink{ch: make(chan event.Event, 1024)}
ctrl, err := boot.Build(ctx, boot.Options{
    Model:    "deepseek-flash",
    Sink:     event.Sync(sink),  // 线程安全封装
    Stderr:   os.Stderr,
})
if err != nil { /* ... */ }
defer ctrl.Close()

// 3. 异步消费事件流
go func() {
    for e := range sink.ch {
        switch e.Kind {
        case event.TurnDone:
            fmt.Println("turn done:", e.Err)
        case event.ToolDispatch:
            fmt.Println("tool:", e.Tool.Name)
        case event.ApprovalRequest:
            // 自动审批
            ctrl.Approve(e.Approval.ID, true, false, false)
        }
    }
}()

// 4. 启动一轮（Send 内部自动执行 goal loop，直到模型回复 [goal:complete]）
ctrl.Send("分析这个项目的架构")
// 或设置目标自动执行
ctrl.SetGoal("重构 internal/boot/boot.go 的 Build 函数")
ctrl.Send("开始执行")
// 或同步运行
// err := ctrl.Run(ctx, "分析这个项目的架构")
// 或同步单轮
// err := ctrl.RunTurn(ctx, "分析这个项目的架构")

// 5. 需要时取消
// ctrl.Cancel()
```

|------|------|:----:|------|

## 五、Go 集成实操建议

### 5.1 接入方式选择

| 方式 | 实现路径 | 复杂度 | 推荐场景 |
|------|---------|:------:|---------|
| **Go Module 直接调用** | fork → 改 module path → import `boot` + `control` | 高 | 需要深度定制工具集、审批策略、会话管理、checkpoint/rewind 等高级能力 |
| **子进程 CLI 调用** `reasonix run "prompt"` | 用 Go 的 `exec.Command` 包装 | 低 | 快速集成，不需要流式输出或交互式审批 |
| **子进程 ACP** `reasonix acp` | stdin/stdout JSON-RPC | 中 | 需要多会话管理但不想处理 Go 依赖 |

> 注意：Go 集成若需要 checkpoint/rewind、goal loop、memory 管理、MCP 热添加等能力，必须走 Go Module 直接调用路径。

### 5.2 Go 集成的关键约束

```
你的 Go 服务
  │
  ├─ fork Reasonix 项目，修改 go.mod module 名 → myreasonix
  │  （原因：internal/ 包不能被外部 import）
  │
  ├─ import "myreasonix/internal/boot"
  │  └─ boot.Build(ctx, boot.Options{...})
  │
  ├─ 或者自行绕过 boot.Build，直接组装 control.Controller
  │  └─ control.New(control.Options{
  │        Runner:    agent.New(...),
  │        Sink:      yourSink,
  │        Policy:    permission.NewPolicy(...),
  │        SystemPrompt: "...",
  │        SessionDir:   "...",
  │        ...
  │     })
  │
  ├─ 需要提供 TOML 配置文件或手动构造 config.Config
  │
  └─ 需要实现 event.Sink 接口接收事件流（位于 internal/event/ 包）
```

### 5.3 建议保持稳定的接口

以下接口一旦修改会波及 CLI 和 Go 集成两条线，二开中应优先保持稳定或用适配器隔离：

1. **`control.Controller`** 核心公共方法（Send / Cancel / Approve / Run / History / Snapshot / Resume / Close）
2. **`event.Sink`** 接口（Emit）
3. **`event.Event`** 结构和 Kind 枚举（新增 Kind 应以 iota 追加而非插入，保持向后兼容）
4. **`boot.Options`** 结构体（Build 入参）
5. **`agent.Session`** 的序列化格式（JSONL）
6. **`config.Config`** 的 TOML Schema（至少向后兼容）

### 5.4 建议在 Go 集成中直接砍掉的前端包

| 包 | 行数 | 理由 |
|----|:---:|------|
| `internal/cli/` | 16,392 | TUI 完全不需要，保留 `cli.go` 可能产生配置互相影响 |
| `internal/acp/` | 2,021 | ACP 协议前端，与 Go 集成路径无关 |
| `internal/serve/` | 1,339 | HTTP/SSE 前端，与 Go 集成路径无关 |
| `desktop/` | 14,761 | 桌面应用全部代码，完全无关 |

## 六、已知改进机会

1. **利用 controller 已有的 goal loop 替代 TUI 的 `/loop`**：controller 的 `SetGoal()/Goal()/ClearGoal()` + `runGoalLoopWithRaw` 已实现了自动目标循环能力，Go 集成可直接使用，无需再从 TUI loop.go 提取
2. **`run` 模式增加自动中间保存**：利用 `ctrl.SnapshotActivity()` 的自动保存机制增强 `run` 模式可靠性
3. **移除外层 `internal/` 目录限制**：将 `control.Controller` 和 `boot.Build` 的公共 API 迁移到 non-internal 路径（如 `pkg/reasonix/`），使其可被外部 Go module import
4. **简化事件类型体系或提供 sink 辅助库**：18 种 EventKind + Partial 两阶段下发 + ToolProgress 流式输出，对前端集成者理解成本仍偏高；可提供 `event.Renderer` 辅助库
5. **废弃 `SetBypass` 的兼容期清理**：`SetBypass` 当前只是 `SetAutoApproveTools` 的别名，文档上已标注为旧名，应考虑在下一个大版本移除
