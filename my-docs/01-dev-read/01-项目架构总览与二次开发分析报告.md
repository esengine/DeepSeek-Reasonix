# Reasonix 二次开发深度分析报告

> 专注范围：CLI 模式 + Go 集成模式（直接调用 Go API）  
> 分析目标：识别影响两种模式可用性、可维护性、可扩展性的技术风险，指导二开决策  
> 基于分支：`main-v2`（commit `e516edcd`）

### 1.2 架构分层

```
cmd/reasonix/main.go              ← 入口：注册 provider + tool，调用 cli.Run
  │
  └─ internal/cli/cli.go          ← 命令路由：run / chat / serve / acp / setup / ...
       │
       └─ boot.Build()            ← 组装中心：config → provider → tool registry
            │                          → permission gate → agent → controller
            │
            ├─ control.Controller ← 传输无关会话引擎（Send / Cancel / Approve / ...）
            │                        【唯一集成面】
            │
            ├─ chat TUI           ← bubbletea Model（chat_tui.go, 110KB）
            ├─ HTTP/SSE serve     ← 浏览器前端（internal/serve/）
            ├─ ACP stdio          ← JSON-RPC over stdio（internal/acp/）
            └─ [Go 集成]          ← 外部 Go 服务直接调用 boot.Build + control.Controller
```

### 1.3 关键依赖

| 依赖 | 用途 | Go 集成是否必须 |
|------|------|:---------------:|
| `BurntSushi/toml` | 配置解析 | ✅ 是（config 包依赖）|
| `golang.org/x/net` | HTTP client | ✅ 是（provider/plugin 网络）|
| `charm.sh/bubbletea/v2` | TUI 框架 | ❌ 否（CLI 独有）|
| `charm.sh/bubbles/v2` | TUI 组件 | ❌ 否 |
| `charm.sh/lipgloss/v2` | 终端样式 | ❌ 否 |
| Go 1.25 + toolchain 1.26.4 | 语言版本 | ✅ 是 |

**关键观察**：`boot.Build` → `control.Controller` 是主干，不依赖任何 TUI 依赖。Go 集成只需要 `internal/` 下的核心包，`cli/`、`serve/`、`acp/` 都是可选前端。

## 二、CLI 模式深度分析

### 2.1 命令树

```
reasonix
  ├── (无参数)        → welcome() + 首次运行引导
  ├── chat / code     → 交互式 TUI 会话（bubbletea）
  ├── run "prompt"    → 一次性执行（TextSink 输出到 stdout）
  ├── serve           → HTTP/SSE 服务
  ├── acp             → ACP stdio 服务（二开可砍掉）
  ├── setup / config  → 配置向导
  ├── mcp             → MCP 管理命令
  ├── doctor          → 诊断
  └── init            → /init 提示
```

### 2.2 TUI 架构（chat_tui.go）

- 基于 **bubbletea v2**，不使用 alt-screen，输出直接追加回滚缓冲区
- input + status + approval banner 是仅有的 bubbletea 管理区域
- Autocomplete：`/` 命令补全 + `@` 文件引用补全
- 事件驱动：agent 事件流经 `event.Sink` → channel → `tea.Msg`
- 已包含 `/loop` 命令

**风险**：
1. **chat_tui.go 单文件 110KB** — 函数间耦合深，单文件难以分工
2. bubbletea v2 较新 — 中文社区资料少，调试需读源码
3. 事件类型 ~30 种，自定义渲染需完整理解全部
4. `/loop` 实现在 TUI 层，复用需提取到 controller

### 2.3 `run` 模式的缺失

`reasonix run "prompt"` 缺少会话持久化——代码遗漏非架构限制，`agent.Session.Save/Load`、`ctrl.Resume` 等基础设施完整。

## 三、Go 集成模式深度分析（核心）

> **Go 集成 = 将 Reasonix 作为 Go Module 导入**，直接调用 `boot.Build()` 取得 `*control.Controller`，通过其公共方法驱动 agent。ACP 是独立于 Go 集成之外的 stdio 前端，与 Go 集成路径无关。

### 3.1 集成面：control.Controller 公共 API

```
外部 Go 服务
  │
  └─ import "reasonix/internal/boot"
     └─ import "reasonix/internal/control"
        └─ boot.Build(ctx, opts) → *control.Controller
           │
           ├─ 异步接口
           │   ├─ Send(input)                    ← 启动一轮（自动组合 prompt）
           │   ├─ SendWithRaw(input, raw)        ← 启动一轮（原始 prompt 另传）
           │   ├─ Cancel()                       ← 取消正在执行的轮次
           │   ├─ CancelCtx() context.CancelFunc  ← 返回取消函数
           │   └─ Running() bool                 ← 查询是否正在执行
           │
           ├─ 同步接口
           │   ├─ Run(ctx, input)                ← 同步运行，阻塞直到完成
           │   └─ RunTurn(ctx, input)            ← 同步运行单轮
           │
           ├─ 控制接口
           │   ├─ Approve(id, allow, session, persist) ← 审批工具调用
           │   ├─ SetBypass(on bool)             ← 设置 YOLO 模式
           │   ├─ SetMode(plan, bypass)           ← 设置 gate 模式
           │   ├─ EnableInteractiveApproval()    ← 开启交互式审批
           │   └─ SetPlanMode(on bool)           ← 设置只读模式
           │
           ├─ 会话接口
           │   ├─ History() []provider.Message    ← 读取对话历史
           │   ├─ Snapshot() error               ← 持久化到磁盘
           │   ├─ Resume(session, path)          ← 恢复会话
           │   ├─ SetSessionPath(path)           ← 设置持久化路径
           │   ├─ SessionPath() string           ← 当前会话路径
           │   ├─ SessionDir() string            ← 会话存储目录
           │   └─ NewSession()                   ← 清空会话（/new）
           │
           ├─ 状态接口
           │   ├─ Label() string                 ← 模型标签
           │   ├─ SystemPrompt() string          ← 系统提示词
           │   ├─ Bypass() bool                  ← YOLO 状态
           │   ├─ PlanMode() bool                ← 只读模式状态
           │   ├─ Branches()                     ← 分支列表
           │   └─ Jobs() []jobs.View             ← 后台任务状态
           │
           ├─ 动态配置
           │   ├─ AddMCPServer(spec)             ← 热添加 MCP 服务器
           │   ├─ RemoveMCPServer(name)          ← 移除 MCP 服务器
           │   ├─ ConnectConfiguredMCPServer()   ← 连接已配置服务器
           │   └─ DisconnectMCPServer(name)      ← 断开连接
           │
           ├─ 资源管理
           │   ├─ Close()                        ← 释放所有资源
           │   └─ HistorySize() int              ← 对话轮数
           │
           └─ 事件输入（你需实现 event.Sink）
               └─ Emit(event.Event)              ← 接收 agent 的流式事件
```

### 3.2 boot.Build 组装流程

```
boot.Build(ctx, opts)
  ┌─ 配置层 ─────────────────────────────────┐
  │ 1. config.LoadForRoot(root) → TOML 配置   │  ← 依赖配置文件和环境变量
  │ 2. ResolveModel(modelName) → provider     │  ← 必须配置至少一个 provider
  │ 3. event.Sync(sink) → 线程安全封装        │  ← 你的 event.Sink 实现
  ├─ 基础设施层 ──────────────────────────────┤
  │ 4. jobs.NewManager(sink)                  │
  │ 5. NewProviderWithProxy → LLM provider     │  ← 联网
  │ 6. 组合 system prompt (memory + skill)    │
  ├─ 工具层 ──────────────────────────────────┤
  │ 7. tool.NewRegistry → 注册中心             │  ← 核心：所有工具注册于此
  │ 8. 启动 MCP plugin Host (按 tier)         │  ← 可选
  │ 9. permission gate + policy               │
  ├─ 扩展层 ──────────────────────────────────┤
  │ 10. command.Load → slash 命令             │
  │ 11. hook.NewRunner → 生命周期钩子          │
  ├─ Agent 层 ────────────────────────────────┤
  │ 12. 构建 executor Agent                    │  ← 核心执行循环
  │ 13. 可选：planner_model → Coordinator      │
  │ 14. 可选：auto_plan_classifier             │
  └─ control.New → 返回 controller ───────────┘
```

### 3.3 event.Sink 接口——你需要实现的核心接口

```go
// 你只需实现这一个接口来接收 agent 的完整输出
type Sink interface {
    Emit(event Event)
}

type Event struct {
    Kind      EventKind        // ~30 种
    Text      string           // 文本内容
    Tool      Tool             // 工具调用/结果
    Level     EventLevel       // info/warn/error
    Err       error
    Time      time.Time
    // ... 更多字段
}
```

事件流生命周期：
```
Send("写一个测试") →
  [TurnStart] → [ModelBegin] → [ToolDispatch(read_file)] → [ToolResult]
  → [ModelBegin] → [ToolDispatch(edit_file)] → [ApprovalRequest] ← 需审批
  → [ToolResult] → [ModelBegin] → ... → [TurnDone{Err: nil}]
```

**重要**：ApprovalRequest 事件需要你通过 `ctrl.Approve(id, true, ...)` 回复，否则 agent 会阻塞等待。

### 3.4 Go 集成的典型用法

```go
// 1. 准备 event sink
type mySink struct{ ch chan event.Event }
func (s *mySink) Emit(e event.Event) { s.ch <- e }

// 2. 组装 controller
sink := &mySink{ch: make(chan event.Event, 1024)}
ctrl, err := boot.Build(ctx, boot.Options{
    Model:    "deepseek-flash",
    Sink:     event.Sync(sink),  // 线程安全封装
    Stderr:   os.Stderr,
})
if err != nil { /* ... */ }
defer ctrl.Close()

// 3. 异步消费事件流
go func() {
    for e := range sink.ch {
        switch e.Kind {
        case event.TurnDone:
            fmt.Println("turn done:", e.Err)
        case event.ToolDispatch:
            fmt.Println("tool:", e.Tool.Name)
        }
    }
}()

// 4. 启动一轮
ctrl.Send("分析这个项目的架构")
// 或同步运行
// err := ctrl.Run(ctx, "分析这个项目的架构")

// 5. 需要时取消
// ctrl.Cancel()
```

## 四、风险矩阵

### 4.1 CLI 模式专项风险

| 编号 | 风险 | 等级 | 说明 |
|------|------|------|------|
| C1 | `chat_tui.go` 单文件 110KB | 🔴 高 | 函数间状态耦合深，任何 TUI 改造都涉及这一文件 |
| C2 | bubbletea + lipgloss 技术栈锁定 | 🟡 中 | 定制 TUI 交互需熟悉 charm.sh 全家桶，社区资料少 |
| C3 | `/loop` 实现埋在 TUI 层 | 🟡 中 | `loop.go` 方法是 `chatTUI` 的方法，无法在 `run` 模式复用 |
| C4 | `run` 模式无会话持久化 | 🟢 低 | 代码遗漏非架构限制，对 Go 集成无影响 |
| C5 | bubbletea v2 未大规模生产验证 | 🟡 中 | Go module API 可能存在不稳定风险 |
| C6 | TUI 测试覆盖不足 | 🟡 中 | 缺少端到端 TUI 交互测试 |

### 4.2 Go 集成模式专项风险（核心关注）

| 编号 | 风险 | 等级 | 说明 |
|------|------|:----:|------|
| G1 | **`boot.Build` 单函数 945 行，依赖 TOML 配置** | 🔴 高 | 所有组件组装逻辑集中于此；集成方必须提供完整 TOML 配置文件（或绕过它自行组装 controller），否则 `config.Load` 会失败。任何配置字段变更都需同步 |
| G2 | **`internal/` 包不在 Go module 发布版中** | 🔴 高 | 该项目的 Go module 没有 release tag，`internal/` 包名按 Go 规范只能在 module 内部使用。外部项目 import `reasonix/internal/control` 会出现 `use of internal package not allowed` 错误。解决方法：需 fork 后修改 module path 或移除 `internal/` 目录限制 |
| G3 | **事件类型 ~30 种，无官方文档** | 🟡 中 | 前端集成需阅读 event.go 源码理解每种 EventKind 含义，选择性渲染成本高 |
| G4 | **ApprovalRequest 是同步阻塞的** | 🟡 中 | 任何触发审批的工具（默认的 writer/bash）都会暂停 agent，等待 `ctrl.Approve()` 回复。无人值守场景需要 `ctrl.SetBypass(true)` 或 `ctrl.SetMode(false, true)` |
| G5 | **MCP 插件 tier 启动增加时序复杂度** | 🟡 中 | eager/lazy/background 三档启动策略导致工具就绪时机不可预期，需等待或检查状态 |
| G6 | **`config.LoadForRoot` 依赖文件系统** | 🟡 中 | 每调用一次 `boot.Build` 都会读磁盘；配置层级（项目 TOML → 用户 TOML → 默认值）的合并逻辑隐含状态。集成方需要理解配置优先级规则 |
| G7 | 多会话需自行管理 controller 实例 | 🟢 低 | 每个 `*control.Controller` 是一个独立会话，资源消耗（MCP 子进程、HTTP 连接）需集成方自行跟踪 |
| G8 | Provider 注册用 blank import | 🟢 低 | `_ "reasonix/internal/provider/openai"` 需确保在 main 或 import 链中执行，否则 provider 不可用 |
| G9 | CodeGraph ~45MB 后台下载 | 🟢 低 | 离线/受限网络环境可能超时失败 |
| G10 | Go 1.25 + toolchain 1.26.4 较新 | 🟢 低 | CI 镜像需自行准备工具链 |

### 4.3 跨层风险

| 编号 | 风险 | 等级 | 说明 |
|------|------|:----:|------|
| X1 | `desktop/` + `cli/` + `acp/` + `serve/` 占用约 31K 行浏览噪音 | 🟡 中 | 编译不链接，但代码浏览和全文搜索会产生干扰；可考虑二开时剥离 |
| X2 | 配置系统多级叠加（项目 + 用户 + 默认） | 🟡 中 | 排查配置问题的调试成本较高 |
| X3 | 系统提示词组合逻辑复杂 | 🟡 中 | 涉及 outputstyle + memory + skill 多层叠加，修改 system prompt 需理解全部叠加层 |
| X4 | provider 扩展需修改 boot.Build 的 init 导入链 | 🟢 低 | 新增 provider 要在 `cmd/reasonix/main.go` 或 `boot` 包中添加 blank import |

### 4.4 二开策略风险

| 编号 | 风险 | 等级 | 说明 |
|------|------|:----:|------|
| S1 | 依赖上游 main-v2 同步 | 🟡 中 | 二改代码与上游变更冲突高发区：`boot.Build` 和 `config.Config` |
| S2 | **`internal/` 目录限制需要解决** | 🔴 高 | 要么 fork 后修改 module path 移除 internal 限制，要么将核心 API 迁移出 internal |
| S3 | CLI 改造和 Go 集成的演进方向可能冲突 | 🟡 中 | CLI 目标是人机交互的 TUI 增强；Go 集成目标是程序化 API。两者对 controller 的需求可能不同步 |
| S4 | `control.Controller` 测试覆盖不足 | 🟡 中 | 单元测试较少，集成测试主要在 `agent/` 的 e2e。对 Go 集成方来说，需要自行补充集成测试 |

## 五、Go 集成实操建议

### 5.1 接入方式选择

| 方式 | 实现路径 | 复杂度 | 推荐场景 |
|------|---------|:------:|---------|
| **Go Module 直接调用** | fork → 改 module path → import `boot` + `control` | 高 | 需要深度定制工具集、审批策略、会话管理 |
| **子进程 CLI 调用** `reasonix run "prompt"` | 用 Go 的 `exec.Command` 包装 | 低 | 快速集成，不需要流式输出 |
| **子进程 ACP** `reasonix acp` | stdin/stdout JSON-RPC | 中 | 需要多会话管理但不想处理 Go 依赖 |

### 5.2 Go 集成的关键约束

```
你的 Go 服务
  │
  ├─ fork Reasonix 项目，修改 go.mod module 名 → myreasonix
  │  （原因：internal/ 包不能被外部 import）
  │
  ├─ import "myreasonix/internal/boot"
  │  └─ boot.Build(ctx, boot.Options{...})
  │
  ├─ 或者自行绕过 boot.Build，直接组装 control.Controller
  │  └─ control.New(control.Options{
  │        Runner:  agent.New(...),
  │        Sink:    yourSink,
  │        Policy:  permission.NewPolicy(...),
  │        ...
  │     })
  │
  ├─ 需要提供 TOML 配置文件或手动构造 config.Config
  │
  └─ 需要实现 event.Sink 接口接收事件流
```

### 5.3 建议保持稳定的接口

以下接口一旦修改会波及 CLI 和 Go 集成两条线，二开中应优先保持稳定或用适配器隔离：

1. **`control.Controller`** 公共方法（Send / Cancel / Approve / History / Snapshot / Resume）
2. **`event.Sink`** 接口（Emit）
3. **`boot.Options`** 结构体（Build 入参）
4. **`agent.Session`** 的序列化格式（JSONL）
5. **`config.Config`** 的 TOML Schema（至少向后兼容）

### 5.4 建议在 Go 集成中直接砍掉的前端包

| 包 | 行数 | 理由 |
|----|:---:|------|
| `internal/cli/` | 13,736 | TUI 完全不需要，保留 `cli.go` 可能产生配置互相影响 |
| `internal/acp/` | 2,000 | ACP 协议前端，与 Go 集成路径无关 |
| `internal/serve/` | ~1,500 | HTTP/SSE 前端，与 Go 集成路径无关 |
| `desktop/` | 14,437 | 桌面应用全部代码，完全无关 |

## 六、已知改进机会

1. **将 `/loop` 从 TUI 提取到 controller**：使 Go 集成也能使用自动循环能力
2. **`run` 模式增加会话持久化**：填补代码遗漏，Go 集成方可直接复用
3. **移除外层 `internal/` 目录限制**：将 `control.Controller` 和 `boot.Build` 的公共 API 迁移到非 internal 路径，使其可被外部 Go module import
4. **简化事件类型体系**：减少前端集成的理解成本
